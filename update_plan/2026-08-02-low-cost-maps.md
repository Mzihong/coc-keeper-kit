## 问题

diff 不可读,三模型(Claude / Gemini / ChatGPT)之间也无法复用。

移植取舍:

- ✅ **灰阶、留白、粗实心黑墙(外墙粗内墙细)**——照抄
- ✅ **编号圆圈**——只用在**城市/区域尺度**;室内图按书里的做法**把房间名写在房间里**
- ❌ **斜视投影**——不做,正投影更好画也更好读(室内图本来就是正投影)
- ❌ **纹理填充**(森林点簇、果园网格、葡萄藤横纹)——不做,改用浅灰形状 + 标签文字。
  信息一点没少,那些点是纯美术
- ❌ **手绘抖动线条**——见下,已否决

**2. DSL 范围 → A 档落地,B 档作可选层,C/D 完全否决。**

| 档 | 内容 | 结论 |
|---|---|---|
| **A** 纯房间盒 | 矩形房间 + 门/窗 + 编号圆圈 + 图例 | ✅ **先落地跑通** |
| **B** + 家具图标 | 沙发/床/桌/书架/壁炉/楼梯… | ✅ **可选层**,只在功能二用 |
| **C** + 地板材质与阴影 | `<pattern>` 填充、墙体加厚、投影 | ❌ **完全否决** |
| **D** + 手绘感抖动线条 | 直线拆段加随机偏移、双重描边 | ❌ **完全否决** |

**否决理由留档,防止以后重开:** C 的成本陡升而收益走平——地板材质不影响任何跑团决策,
它是美术需求不是功能需求。D 虽然最贴阿卡姆观感,但随机性会让同一份 DSL 每次渲染出不同
SVG,**diff 全红**,必须额外引入 seed 机制才能复现,且每改一次都要肉眼验收。两者都被
否决,渲染器因此是**纯确定性的**——同样输入必然同样输出,这条是本计划的硬约束。

**3. 是否值得做 → 值得,而且是两个功能不是一个。** 见下。

## 方案:两个功能,共用一个渲染器

**这不是同一张图的两种画法,是两件不同的产物,给不同的人看。**

| | **功能一:场景定位图** | **功能二:可互动场景图** |
|---|---|---|
| 给谁 | **KP**,跑团时自己看 | **PL**,摆到桌上一起看 |
| 用途 | 快速定位、判断连通与视线 | 具体场景里和玩家互动 |
| 档位 | **A** | **A + B(家具层)** |
| 模型每次写(10 间房) | ~15 行 JSON | ~50–70 行 JSON,且要先读房间描述再判断家具布局 |
| 预估 token | ~400 | ~1500–2000,**约 3–5×** |
| 何时生成 | 场景生成时可顺手带上 | **必须 KP 主动要**,不自动生成 |
| 剧透 | 可含 KEEPER ONLY(暗门、秘密) | **必须 player-safe** |
| 落盘 | 场景 md 的 Map 小节 | `campaigns/<slug>/handouts/` + 渲染的 svg |

**成本必须告知。** 功能二比功能一贵 3–5 倍,而且贵在模型侧(要为每间房挑家具、判断朝向
与是否越墙),不是渲染侧。**生成前先把预估成本说给 KP 并等确认**——这条要写进 spec,
不是写进本计划就算数。上面的倍数是**估算,阶段 2 首次落地时实测回填**。

**剧透是功能二的硬门槛。** 一张递给玩家的图就是 player-facing prop,受 `core/11-review.md`
的剧透审查管:暗门、KEEPER ONLY 的房间用途、编号对应的秘密都不能出现在玩家版上。
同一份 DSL 要能渲两版(`--player` 开关过滤掉标了 `secret: true` 的元素),**不是让模型
写两份 DSL**——写两份必然不同步。

      不再是"本地若有"。)
- [ ] `scripts/render-map.py` — DSL→SVG,**无外部依赖,stdlib 即可**;纯确定性
- [ ] DSL 定型:房间 `{id, name, x, y, w, h, doors[], windows[]}`;门窗用「哪条边 + 边上位置」
      表达,不用绝对坐标(模型算绝对坐标必错)
- [ ] **渲染要素照 `interior-1/2/4` 的体例**(下列每一条都有样本可对):
      - 墙:**粗实心黑,外墙粗内墙细**。这只是加大 stroke-width,**免费**
        ——别和 C 档否决掉的「墙体厚度建模 + 投影 + 材质」混为一谈
      - 门:**墙上开口 + 一个 ∧ 形楔子**(不是弧线)
      - 窗:**外墙外侧的短虚线段**
      - 楼梯:**横线阴影矩形 + 箭头 + 「向上/向下」**
      - 圆形塔楼直接画圆
      - **房间名写在房间里**,居中一行。中文短,`text-anchor="middle"` 就够
        ——原来"只画编号不写名字"那条已按样本推翻,编号圆圈留给城市尺度
      - 引线标注(箭头 + 文字):`interior-1` 的「上锁的门 **?**」「钉着木板的窗户和约束装置」

## 阶段 2 — 功能二:可互动场景图(B 家具层,可选)

- [ ] **不建图标库。家具 = 几何图元 + 标签文字。** 依据是 `interior-4`(密大图书馆)——那张图
      家具密度很高,但**没有一个是图标**:书架是细长矩形、阅览桌是圆、阶梯教室座位是
      同心弧加点、讲台办公桌是矩形。**形状只负责占位,含义全在标签里**(报纸/期刊合订本/
      旧书/工程学/冶金学/地理学)。

      > **这条推翻了本计划初稿的「图标库封顶 12 个」。** 初稿担心的"永远增长的美术资产"
      > 因此根本不存在,B 档的渲染器规模从 ~350 行掉到 ~200 行(图标 path 常量本来占一半),
      > 模型写的也从"挑图标编号"变成"写标签"——后者才是它擅长的事。
- [ ] 家具 DSL 用图元不用类型枚举,坐标**相对所在房间**,不是全图绝对坐标:
      ```json
      "furniture": [{"s": "rect",   "x": 1, "y": 0.5, "w": 2, "h": 0.4, "label": "书架"},
                    {"s": "circle", "x": 3, "y": 2,   "r": 0.6,          "label": "阅览桌"}]
      ```
- [ ] 渲染器加**越界与重叠检查**:家具画到墙外或互相压住时报错,不静默出图
      (这是 B 档最容易翻车的地方)

## 阶段 2b — 室外站点图(2026-08-04 定案:不新增图种,不新增渲染器)

庄园/野外场景**要出图**,但**不为它单写渲染器**。把 `site-crowninshield-manor` 拆开看,
它需要的东西 A/B 档已经在做了——**"没有墙的画布"不是新功能,就是房间数组为空、只有图元层**:

| 庄园图上的东西 | 用什么画 | 新功能? |
|---|---|---|
| 森林 / 果园 / 花园(区域) | 带标签的大矩形或圆 | ❌ B 档图元 |
| 公馆 / 车库 / 储藏室 | 小实心矩形 + 标签 | ❌ B 档图元 |
| 「大理石圆形建筑」 | 小圆 + 标签 | ❌ B 档图元 |
| 引线标注 | 箭头 + 文字 | ❌ 阶段 1 已有 |
| **小路 / 溪流** | **折线** | ✅ 唯一新图元 |
| 指北针 | 角落固定图形 | ✅ 城区图也有 |

- [ ] 折线图元:`{"s": "path", "pts": [[x,y],…], "label": "小路,步行 5 分钟",
      "style": "solid|dashed"}`。**约 15 行**
- [ ] 指北针图元,固定画在角落。**约 5 行**
- [ ] **不做纹理填充**(森林点簇、果园网格、葡萄藤横纹)——浅灰形状 + 标签文字即可,
      与 C 档否决保持一致
- [ ] **克制规则:站点图目标 5–9 个元素,超过就该拆两张或改用文字。** 依据是书里那张
      农场站点图——只有「高地 / 虚线区域 / 毁坏的农场房屋 / 井」四个元素,照样可用
- [ ] 图上表达不了的东西(从公馆能否看到森林、跑过去多久)**写进场景正文,不让图背责任**
      ——这正是阿卡姆的做法:城区图上只有编号,细节全在正文

**为什么不另造一套文字格式:** 省的不只是那 20 行代码,是**不用再教模型第三种写法**。
站点图和室内图共用同一份 DSL 语法,模型学一次就够。

# Update Plan — 模组多样性:掷骰走脚本 + 补缺表 + 提高掷骰频率

> 日期:2026-08-04
> 状态:待执行(方向已于 2026-08-04 二次会话定案)
> 来源:Keeper 2026-08-04 会话——先问「1d20 会不会太少了,能不能拓展 1d100」,
> 同日重述为「**想要 100 条的根本原因是希望做出来的模组具有多样性,否则每个模组都发生在
> 类似场景中战斗未免太枯燥无味**」,并追加一条硬要求:**掷骰必须用 `.py` 取伪随机,
> 不能让大模型决定**
> 前置:无。与 P12 有软耦合(都动 `reference/tables/`,别同批 commit)

## 这份计划换过一次方向

**原方向(已推翻)**:把 `reference/tables/` 的表从 d20 扩到 d100,约 390 条新条目。

**推翻的理由是它的前提在数学上不成立。** 四张种子表现在是 20⁴ = **16 万种组合**,
扩到 d100 是 1 亿。守秘人这辈子跑不到 160 场团——**"组合空间被 20 条封顶"不是真的**。
如果实际感觉每个模组都像同一个,原因一定在别处,写 320 条不会解决它。

原方向里唯一站得住的观察是**"20 条会被很快摸熟"**。但那是**采样问题不是长度问题**——
详见下面的诊断第 ①、③ 条。老约定(`tables/README.md`「宁可 20 条具体的,也不要 100 条
含糊的」)因此**不必推翻,原样保留**;新方案是多开几张 20 条的表,不是把一张表灌到 100。

## 目标

**让两件事变得不一样:模组与模组之间,以及一个模组内部的场景与场景之间。**
不以骰面数为目标,以「掷骰真的均匀」「该掷的地方有表可掷」「掷得够勤」为目标。

## 诊断:多样性漏在哪四处

### ① 模型掷骰不是均匀的(**最上游,也是 Keeper 点名要修的那条**)

`core/01-intake.md` 说 "Roll; don't pick the first plausible thing you think of",但没有任何
机制保证这件事——模型口头报的点数会偏向表里写得最勾人的那几条。**这一条不修,后面三条
全部打折**:扩到 100 条的结果只是它从 100 条里挑同样那 10 条,摸熟速度分毫不变。

### ② 真正雷同的那个维度,现在的条目数是 0 不是 20

Keeper 点名的「每个模组都在类似场景里战斗」——**kit 里没有任何一张表掷对抗场面**。
[`core/04-design-scenario.md:40`](../core/04-design-scenario.md) 给场景分类是
clue / choice / shock / breather,**战斗连一个节点类别都不是**;`tables/` 十三张表里没有
一张管地形、双方数量、环境里能用的东西、为什么跑不掉。于是每次都是现场即兴,而即兴的
对抗场面必然收敛到仓库 / 地下室 / 夜里的码头 / 一群邪教徒围上来。

**从 0 写到 20 条的收益远大于把 `locations` 从 20 写到 100**,成本是 20 条对 80 条。

同一类缺口还有一处更上游的:**模组的形状**。`core/04` 的 "Build in this order" 每次产出
同一副骨架,而「一夜之间 / 三个月的通信往来 / 围城 / 旅途 / 倒计时仪式 / 只追一个人」
这一维**从来没有被掷过**。

### ③ 高频表比种子表更容易被摸熟,而原计划的分层正好是反的

| 表 | 一个战役掷几次 | 原计划优先级 |
|---|---|---|
| `npc-quirks` | 每造一个 NPC 一次,**8–15 次** | 种子表,排第 4 |
| `complications` | 每场两次,**6–10 次** | 降级 d50 |
| `locations` | **1 次**(接线后 8 次) | 种子表,排第 2 |
| `hooks` / `mythos-angles` | **各 1 次** | 排第 1、第 3 |

`mythos-angles` 一个战役掷一次,要跑 20 个战役才轮完一圈;`npc-quirks` 两个战役就开始重复,
而且是**在同一个战役内部**重复——那才是牌桌上真能感觉到的雷同。

**算一下**:20 条均匀掷 10 次,出现重复的概率是 **93.5%**(生日悖论)。
换成 d50 是 61.8%,d100 仍有 37%。**靠加长条目治撞车,性价比极低**——
真正治它的是**同一战役内不放回抽样**,见阶段 1。

### ④ `locations` 一个战役只掷一次,扩它只改那一掷

[`locations.md:6`](../reference/tables/locations.md) 自己写着"之后场景需要新地点时再掷",
但 `core/04` 建 scene web 时**没有接这条线**。一个战役掷一次,剩下 8–10 个场景的地点全是
自由创作。**接线是零写作成本的收益**:掷骰次数从 1 涨到 8。

## 拍板结果(2026-08-04)

- ① **不推翻**「宁可 20 条具体的」那句约定——新方案与它不冲突。
- ② **不做全面 d100**。扩容降级为阶段 5 的条件执行项,判据见该阶段。
- ③ **新增硬要求(Keeper)**:掷骰一律走 `scripts/roll.py`,模型不许自己报点数。

## 阶段 1 — `scripts/roll.py`,以及"不许口头掷骰"的硬约定

**这是全计划的地基,先做。** 它一次修掉诊断 ①③ 两条,并让阶段 5 变成可选的。

### 1.1 脚本

- [ ] 新建 `scripts/roll.py`。用 `random.SystemRandom()`,**不接受模型给定的点数**。

```
python scripts/roll.py <table> [<table> ...] [--times N] [--campaign <slug>] [--fresh]
```

- [ ] **解析表文件自己声明的骰面**:开头的 `掷 **1dN**`,或小节标题里的 `(1D10)`,
      以及 markdown 表格第一列的 `dN` 表头。骰面不是从参数里传的,免得传错。
- [ ] **两维表原生支持**:`cult-goals.md` 的 `## 愿望(1D10)` / `## 手段(1D8)`
      各掷一次,一并输出——它本来就规定"两张必须成对使用"。
- [ ] **输出是可原样粘贴的整行条目,不只是点数**:

```
$ python scripts/roll.py locations mythos-angles --campaign dagon-bay
locations.md      1d20 → 13   一处过季的度假地,人手齐全,客房全空
mythos-angles.md  1d20 →  8   某个存在正在死去,它的衰亡本身就是灾难
```

- [ ] **`--campaign <slug>` 记账**:追加到 `campaigns/<slug>/rolls.log`(表名 / 点数 /
      条目 / 掷它的 spec)。这份记账是后两个功能的数据源,也让守秘人能回看本战役掷过什么。
- [ ] **同一战役内不放回**(给了 `--campaign` 即默认开启):掷到本战役已用过的条目就重掷。
      **这一条直接把上面那个 93.5% 打到 0**,而且不用写一条新条目。表掷空时放行并注明
      "本表已掷空,开始重复"。
- [ ] **`--fresh` 跨战役查重**:掷出的条目若在其他 `campaigns/*/rolls.log` 里出现过就重掷
      (上限 20 次,仍撞就放行并注明)。**这才是"摸熟"的正解**,在 d20 上就成立。
- [ ] **非骰表要报错不要硬掷**:`cultist-archetypes.md` / `monster-traits.md` /
      `monster-index.md` 走显式排除名单,给出"这不是骰表"的提示。
- [ ] **自检:每张表的实际行数必须等于骰面数**,不齐就非零退出。
      顺带补上一个现有校验的盲区——`build-reference-index.py` 查的是文件级引用与孤儿,
      **表里少一行、多一行它看不见**(同一族失败在 `WORKLOG.md` 里已经记过两次)。
- [ ] `--seed` 仅供测试,**不写进任何 spec**。

## 阶段 3 — 新表 `confrontation-grounds.md`(d20)

**直击 Keeper 点名的那件事。** 掷的是**对抗场面成立的条件**,不是"打不打得起来":

- 地形与它带来的限制(高低差、水、暗、窄、易燃、人多)

## 风险与边界

1. **模型可能绕过脚本。** 这是本计划最大的执行风险——`core/` 里写"必须跑"不等于它会跑。
   挡法有三层:产物里必须附命令与原始输出、`rolls.log` 落盘、`core/11` 判 fail。
   三层都是事后可查的,不依赖自觉。
2. **python 不一定在。** kit 已经依赖 python(`render-investigator.py`),但掷骰是**每次
   生成都要用**,依赖等级比渲染卡面高一档。降级路径必须写死:**请守秘人手掷,不许自己编**。
   降级发生时要**在产物里注明**,否则事后分不清哪次是脚本掷的。
3. **`rolls.log` 是新的战役级文件**,`campaigns/_template-campaign/` 要不要预置空文件、
   要不要进 `core/01` 的 Output 六项清单——阶段 1.1 落地时一并定。
4. **凑数就是失败**(从原方案保留):新表宁可 20 条具体的。阶段 4 的"5 条试水"就是这条的
   实证检验,写不出区分度就砍掉整个阶段。
5. **和 P12 的边界:`madness.md` 不归本计划**,它是规则书表VII 的转录,长度由书决定。
   两个计划都动 `reference/tables/`,**别同批提交**。

## 被推翻的原方案(留档)

原计划的主体是「四张种子表 → d100 / 备课表 → d50 / 合计约 390 条 ~600 行」,并要求先推翻
`tables/README.md` 那句成文约定。**推翻理由见本文开头**:组合空间从来不是瓶颈,而它真正
想治的"摸熟"是采样问题,由阶段 1 的脚本以近乎零写作成本解决。原方案里同时考虑过的
「乘法路线」(两张 d10 相乘 = 100 组合)一并作废——它要求两维真正正交,硬拆出来的废组合
会给 `core/01` 的"take what you get"开后门,而现在也不再需要用它省成本。
